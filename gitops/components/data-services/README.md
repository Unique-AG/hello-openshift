# Data services — sync wave 3

The stateful services that replace the AWS managed data tier. Each is an
operator custom resource, so this layer cannot apply before the operators in
wave 1 have Established their CRDs.

| Service | Replaces | Custom resource | Operator |
| --- | --- | --- | --- |
| PostgreSQL | Aurora PostgreSQL | `Cluster` + `Database` | CloudNativePG |
| Redis | ElastiCache | `RedisReplication` + `RedisSentinel` | Redis Operator (Opstree) |
| MinIO | — | `Tenant` | MinIO Operator |

Object storage for applications is NooBaa, provisioned in wave 2 via
`ObjectBucketClaim`; MinIO here covers the cases that want an S3 API of their
own.

## Credentials work differently per service

This is the part worth reading before debugging an authentication failure.

- **Redis and MinIO** credentials are generated by Terraform (`1-foundation`)
  straight into AWS Secrets Manager, and External Secrets syncs them in over
  IRSA. They survive a cluster rebuild.
- **PostgreSQL** credentials are generated **in-cluster by CloudNativePG** and
  never leave it. They are therefore *invalidated by a cluster rebuild*: the
  operator generates a new password for `app_user`, while everything that stored
  the old one — the application ExternalSecrets, the Zitadel database secret —
  still holds the previous value.

  `scripts/sync-db-passwords.sh` re-points every stored credential at the
  current CloudNativePG password. Run it after any rebuild, before concluding
  that a service is broken.

## Databases

`postgres/databases.yaml` declares one `Database` per consuming service rather
than sharing a single database. The Zitadel and configuration-backend databases
in particular are separate because their migrations run independently.

## Ordering within the layer

The `Cluster` must be Ready before the `Database` resources can be reconciled;
CloudNativePG handles that itself, so no sync-wave split is needed inside this
layer. What does matter is that wave 4 (identity) and beyond do not start until
this layer is Healthy — Zitadel fails its migration job against a database that
does not yet exist.
